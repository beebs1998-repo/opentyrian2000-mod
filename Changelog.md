# Changelog

## Gameplay
- Added a Bullet Curves option, toggleable at Setup - Gameplay - Bullet Curves (ON/OFF). ON by default, so stock play is unchanged and an existing `opentyrian.cfg` that predates the key keeps the default. OFF makes every enemy shot fly dead straight from wherever it was fired, the way a CAVE or Touhou shot does.
  - The measurements below are what drove the design, and the first version of this option got them wrong. It was originally scoped to the `tx`/`ty` aim acceleration alone, on the reasoning that "bullets moving along with the ship" must mean tracking. Counting the actual weapon table first would have shown that this gates 6 weapons out of 819 and is invisible in practice.
- The table is parsed from `tyrian.hdt` using the 80-byte record layout in `episodes.c`, where `tx`/`ty`/`aim` sit at offsets 7/8/9 and `acceleration`/`accelerationx` at 74/75. Over the 819 base-bank weapons: `tx` or `ty` is non-zero on 6 (0.7%), `aim` on 51 (6.2%), `acceleration` or `accelerationx` on 218 (26.6%). Note that `doc/tools/weapon.py` disagrees with the C struct -- its format string predates `sg[8]` becoming `u16`, and it assumes 780 weapons where `WEAP_NUM` is 1818 -- so it should not be used to measure this.
  - Four of the six `tx`/`ty` weapons are not fast homing shots: they carry no initial velocity at all and creep toward the player one pixel per tick, so they read as drifting mines. Two are genuine homing shots. Turning the row off and seeing nothing happen is the expected outcome of the narrow version, not a symptom of a broken gate.
  - So the option gates both authored mechanisms that make a shot stop travelling in a straight line: `tx`/`ty` and `acceleration`/`accelerationx`. The name follows the union rather than either mechanism, since "wobble" described only the first and `acceleration` is not a wobble by any name.
  - `tx`/`ty` is the only per-tick coupling in the game between a shot and the ship. Every live shot re-reads `player[0].x`/`player[0].y` each tick and steps its velocity one unit toward it, clamped to `+/-tx`/`+/-ty`. Re-reading the target every tick rather than fixing it at spawn is what makes the curve keep bending after the shot has left the turret, so sidestepping drags the shot's path with you, and what makes the velocity flip sign the instant the shot crosses your centre line.
  - `acceleration` is only ever -1, 0 or +1 per tick across all 819 weapons, which reads as negligible until you compound it: a shot launched at 3 px/tick is past 8 within a few ticks. 174 weapons use +1 and 43 use -1.
  - Turning the option off is therefore NOT a uniform difficulty reduction, and this is the caveat most worth knowing before anyone reaches for it. The 174 accelerating weapons get slower, which is the intended effect. But the 43 decelerating ones currently bleed off speed and hang near the player, and flattened they hold their launch velocity for their entire flight, which makes those strictly harder to dodge. The option is a change in how patterns are authored, not a nerf.
  - A quarter of the weapons change shape as a result. A single accelerating shot is frequently what draws the spiral or the sweep in a pattern; straightened, some of those read sparse. That is inherent to the request rather than a side effect to be tuned away.
  - The spawn-time aim override in `JE_drawEnemy()` is deliberately NOT gated. A shot still points at where the ship was when the turret fired and then commits to that vector, which is what CAVE does -- the difference is that nothing re-aims it afterwards. Gating the spawn aim too would have turned authored patterns into fixed lattices, which is a much larger change than the row's name implies.
  - Only the velocity *inputs* are gated, never the position integration. `sx += sxm` and `sy += sym` stay unconditional because inside a disabled block the shot would freeze in place rather than fly straight, which is the opposite of the intent.
  - The gate is at the point of use rather than zeroing the fields at spawn. The spawn assignment sits inside the Bullet Hell ring loop, so gating there would put an extra branch in that hot path; and "born curving" would leave every shot already in flight curving for the rest of its life after the option changed. Setup is reachable from the pause menu, so that is a real case and not a hypothetical one. The flag is sampled once per tick above the shot loop, since it is a menu setting and every live shot in a tick necessarily sees the same value.
  - The reordering that came with this is a no-op and is worth stating so nobody re-derives it: the `tx` block now runs after `sym += syc; sy += sym` instead of before it. The `tx` block reads and writes only `sx`/`sxm` and the `ty` block only `sy`/`sym`, and neither reads what the other writes. With the flag ON -- the default -- the simulation is bit-identical to stock.
  - Worth being precise about what was already true, because it is the obvious thing to assume and it is not the case: enemy shots were already absolute screen-space objects. They never inherited the background scroll rate (`backMove`/`backMove2`/`backMove3` advance only the map backdrops) and they never inherited ship motion. Everything being gated here is deliberate authoring on top of that, not an artifact of it.
  - `varz.c`/`varz.h` gained `bullet_curves_enabled`; `config.c` persists `[gameplay] bullet_curves` (`on`/`off`), and the binary `tyrian.cfg` layout is unchanged. The key was `bullet_wobble` in one unreleased intermediate build; no migration is written because it never reached a released binary, so no existing config can carry it. There is no `apply*()` step, unlike most options here, because the flag is read directly where shots are updated and there is no subsystem to push it into -- `interp_smooth_motion` is the existing precedent for that. Saving writes the key unconditionally, so a pre-existing config gains an explicit `bullet_curves=on` line on first save, which is a no-op since it equals the default.
  - Deliberately not using `config_get_or_set_bool_option()`, which looks like exactly the right primitive for an option whose default is `true`. It takes its `value` parameter by value, parses into that local copy, and returns it -- the caller's flag is never written. The two-call `config_get_bool_option()`/`config_set_bool_option()` pair is what every other option uses, and that is what this one uses.
  - This is the one option in the fork whose polarity is inverted from the usual: every other option defaults to the stock value and treats the new behaviour as the opt-in, whereas here the opt-in is the *change*. That is what keeps an existing install playing exactly as it did, and it is also why the row description describes the ON state. Note that no sibling row carries a "(CAVE-style)" tag on this one, because CAVE is the game that does not curve -- tagging it would point the wrong way.
  - `--regress-bullet-count` is no longer an invariant for this option. Gating acceleration changes flight times, which changes when shots are culled, so pool occupancy and drawn counts legitimately move between ON and OFF. The flag is usable as a before/after measurement of the change, not as a pass/fail check. It was an invariant only while the option was scoped to `tx`/`ty`, where nothing about culling changed.
  - Not broadcast over the network and not recorded in demos. A two-player network game whose peers disagree about the setting plays differently on each machine but does not desynchronise, since the option adds no `mt_rand()` draws and no spawns; it has the same exposure as `bullet_hell_enabled` and `smoothScroll`. A `demorec.N` recorded with the row ON replays with different bullet paths once it is OFF, again without the RNG stream shifting, so playback does not break.
  - Only the base weapon bank was measured. Weapons 1000-1818 live in the `.lvl` files and load only when `episodeNum > 3`, so episodes 1-4 are fully covered by the figures above and episode 5's custom weapons are not measured at all. Their block boundaries are not derivable from `lvlPos` alone -- the largest block in any level file is 24,865 bytes against the 65,534 a contiguous 819-record bank needs -- so counting them needs runtime instrumentation rather than a file parse.
- Added an optional Bullet Hell mode, toggleable at Setup - Gameplay - Bullet Hell (ON/OFF). Off by default, so stock play is unchanged until it is switched on. The reference is CAVE-style danmaku: density and pattern shape rather than raw bullet speed.
  - Each authored enemy volley is fanned into three rings 14 degrees apart, so a one-shot pattern opens into a roughly 28 degree arc with the authored pattern as the centre. The authored pattern keeps the middle ring and is echoed either side of it; all three rings are spawned from the same one of the weapon's 8 pattern frames, because letting each ring advance `eshotmultipos` spreads them across different frames and reads as a spiral rather than a wall. `BULLET_HELL_RINGS` and `BULLET_HELL_SPREAD_DEG` in `src/varz.h` are the tuning knobs.
  - The rotation is applied after the aim override rather than before, so an aimed shot opens into an n-way aimed fan instead of staying a single beam, which is the shape worth having. Acceleration is deliberately left unrotated so curving patterns stay aligned with the fan they belong to.
  - The aim override is resolved once per authored pattern frame, before the ring loop, not once per ring. Choosing a target in two-player mode draws from the shared `mt_rand()` stream, so resolving it per ring would have consumed that stream three times as fast whenever the mode was on. `mt_rand()` is reseeded deterministically at level start, which is what lets demos replay and two-player network games stay in step, so a mode that quietly shifted the stream would have broken both -- demos would play back wrong with the option on, and peers disagreeing about the setting would desynchronise outright rather than merely see different bullet patterns. Resolving it per frame is also the better shape for the mode: one turret's fan converges on one target instead of being split across both players ring by ring.
  - Bullet speed is not changed at all. Raising it was rejected: the logic tick is about 34.8 Hz (0x4300 * pitPeriod * frameCountMax=2), well under the 60 Hz a CAVE original runs at, so the reaction budget is already tighter than the reference, and `drawlist.c` snaps instead of interpolating any object that moves more than 64 px in a tick.
  - The extra fire rate is tiered so that it does not compound with the halvings the game already applies above Normal and Maniacal. Those bands are `difficultyLevel > DIFFICULTY_NORMAL` for one halving and `> DIFFICULTY_MANIACAL` for a second, so stock already fires about 4x as often at Zinglon and above; stacking another halving on top of that measured as 24x the stock bullet density and pegged the shot pool. Bullet Hell contributes most where stock takes the least: 2x on Easy/Normal, 1.5x from Hard to Maniacal, and nothing above that. Measured total bullet density against stock at a weapon firing every 40 ticks is about 5.7x on Easy/Normal, 8.6x on Hard through Maniacal, and 10.9x on Zinglon and above. The middle band is inclusive of Maniacal because stock only applies its second halving strictly above it; leaving Maniacal out made density fall from 8.6x at Suicide to 5.7x at Maniacal, which is backwards for a mode meant to get harder as difficulty rises.
  - Note which tiers are actually reachable when testing this. The difficulty menu shows only three entries by default: `menuItemsVisibleCount` starts at `menuItemsCount - 3`, so Easy, Normal and Hard are all you get. Impossible appears with Shift+G, Suicide with Shift+], and Zinglon by typing L-O-R-D (or holding all four at once). Insanity, Maniacal, Nortaneous and 10 are never in the menu at all and are reachable only through the score ratchet in `adjust_difficulty()` or through level event 46. So the 8.6x figure is reachable from the menu, but the 10.9x figure needs all three unlocks.
  - Difficulty can be raised mid-level by level event 46, so the tier is re-evaluated per shot and density shifts during a battle rather than being fixed at level load.
  - Bullet Hell turns Small Hitbox on, because it is not survivable on the stock hitbox; in a CAVE original the tiny hitbox is mandatory rather than optional. Turning Small Hitbox off turns Bullet Hell off with it. This is the same mutual-exclusion arrangement `applyStereo()` already uses for Stereo and Surround, which avoids inventing a locked-row concept the menu does not have. `applyBulletHell()` in `varz.c` is the reconciliation point, and `config.c` applies the same rule on load so a hand-edited file cannot leave the two flags inconsistent.
  - `varz.c`/`varz.h` gained `bullet_hell_enabled` plus `applyBulletHell()`; `config.c` persists `[gameplay] bullet_hell` (`on`/`off`), and the binary `tyrian.cfg` layout is unchanged.
  - Combat score is worth more in this mode: 2.0x on Easy/Normal, 1.5x from Hard to Maniacal, 1.25x above that. The bands are deliberately the same as the fire-rate bands, so the mode pays for what it actually costs, and the top band is not zero because the three-ring widening applies at every difficulty even where the rate contribution is nil. Difficulty already scales enemy value up to 8x on its own (`JE_makeEnemy`), so the mode does not compound on top of that beyond what its own bands allow.
  - The surplus is held in a new `Player::bullet_hell_bonus` rather than inflating `cash`. That keeps `cash` at its stock meaning -- it is the shop budget, the galaga life threshold, and the value `adjust_difficulty()` reads to ratchet difficulty -- so the mode does not hand out free shop money, does not hand out galaga lives, and does not feed its own score back into the difficulty ratchet. That last one matters: `difficultyLevel` is broadcast over the network, so a Bullet Hell run that ratcheted itself upwards faster would push a different difficulty onto the other peers.
  - `JE_totalScore()` is deliberately unchanged and still excludes the surplus, so `adjust_difficulty()` reads exactly what it read before. `JE_bulletHellScore()` is the same total plus the surplus, and is what the one-player high-score table and the level-end score readout use. The surplus is credited by `JE_playerScore()`, which replaces the two raw `cash +=` sites that pay for shooting things (the enemy-kill award in `tyrian2.c` and the score-pickup award in `mainint.c`). Item rewards, the power-up consolation and the Timed Battle bonuses are deliberately not routed through it: those are not combat score, and inflating the Timed Battle time bonus would hit a separate leaderboard.
  - The surplus is computed as "what this award would have been worth", rounded, minus the raw value, rather than as `amount * (multiplier - 1)`. The two differ on small awards: at 1.25x a 2-point enemy yields 0.5 under the naive form and truncates to nothing, so every low-value enemy in a Zinglon Bullet Hell run would have silently paid no bonus at all. A 1-point enemy still pays nothing, because 1.25 of one point rounds back to one.
  - The surplus is not persisted. The save format is frozen, so reloading a shop save drops whatever was accrued since the game started. It is reset wherever `cash` is reset.
  - Existing high-score entries are left alone. They were recorded under stock rules, so Bullet Hell runs simply have a higher bar to clear on the same board; there is nothing in `T2KHighScoreType` marking which mode produced a score, and its on-disk layout is frozen.
- Raised `ENEMY_SHOT_MAX` from 60 to 255.
  - 60 was not enough for the mode above, and the way it failed was the real problem. When the spawn path found no free slot it jumped to `draw_enemy_end`, which abandons the rest of that enemy's AI: its remaining turrets and its whole Enemy Launch Routine. So a busy screen did not just fail to draw bullets, it made bosses stop spawning adds mid-fight. Raising the pool makes that far rarer, and the exhaustion path was changed to skip only the rest of the current volley.
  - 255 is a hard ceiling rather than a round number. `drawlist.c` identifies a recorded object by (obj_kind, obj_id, obj_sub) and casts the id to a `Uint8`, so the id is what pairs a bullet with its own position in the previous tick for interpolation. Slot 256 would wrap to 0, and two different bullets would be matched against each other, giving silently wrong lerped positions rather than a crash. There is an `#error` guard next to the define so the next person to raise it finds out.
  - This also changes stock play slightly, and that is the one divergence from upstream here: enemies that used to go silent at 60 live bullets now keep firing. The cost is about 11 KB of static data, and the per-tick loop and the pool allocation scan both scale with the constant.
- Added `--regress-bullet-count`, which reports enemy bullet density per tick: mean and peak shot-pool occupancy, mean and peak drawn shots, and how many volleys were truncated by a full pool. Occupancy and drawn counts are both reported because they answer different questions -- occupancy includes shots the pool had no room for, so it exposes saturation, while drawn is what the player actually sees. It reuses `drawlist-regress.log` and the existing summary path, and is exclusive of the two replay checks because they share that one log.
- Fixed `[gameplay] small_hitbox` in `opentyrian.cfg` ignoring anything but `on`. Its loader compared the raw string against `on`/`ON`/`On` only, so a hand-written `small_hitbox=yes` silently loaded as false, while every other option in the file went through `config_get_bool_option()` and accepted `0`/`1`, `no`/`yes`, `off`/`on` and `false`/`true`. It now uses the same helper as the audio section.

## Audio
- Fixed Stereo and Surround being ignored at startup when set in `opentyrian.cfg`. `applyStereo()` ran from `JE_loadConfiguration()`, which is before `init_audio()`, so the mode request was dropped: `stereo_set_mode()` ignores requests while uninitialized and `stereo_init()` then resets the mode to off. The effect only took effect once the Setup menu was opened. `applyStereo()` now runs immediately after `init_audio()` in `opentyr.c`. Stereo Width was unaffected, because `stereo_set_width()` records the desired width even before init.
- Added an optional reverb/echo effect over the final mixed audio stream (music and sound effects together), toggleable at Setup - Sound - Reverb (ON/OFF). Off by default, so existing audio is unchanged until it is switched on.
  - Added `src/reverb.c`/`src/reverb.h` as a self-contained mono Schroeder reverberator (4 parallel feedback comb filters with one-pole lowpass damping into 2 series allpass filters, DC-normalized). Delay lengths are scaled to the sample rate that SDL actually negotiates.
  - `loudness.c` calls `reverb_init`/`reverb_process`/`reverb_deinit` around the existing mixer; the dry path is untouched, so no latency is added, and the reverb network always runs with a ~30 ms wet-gain ramp so toggling never clicks.
  - `varz.c`/`varz.h` gained `reverb_enabled` plus `applyReverb()`, mirroring the `small_hitbox_enabled`/`applySmallHitbox()` pattern.
  - `opentyr.c` added the `Setup - Sound - Reverb` ON/OFF picker row, following the existing picker-based option pattern.
  - `config.c` persists the setting as a new `[audio]` section key `reverb` in `opentyrian.cfg` (`on`/`off`); the binary `tyrian.cfg` layout is unchanged.
- Added an optional diffuse surround effect, toggleable at Setup - Sound - Surround (ON/OFF), off by default and separate from Stereo.
  - Stereo and Surround are mutually exclusive: both turn the mono mix into the channel pair, so there is nothing to chain one through the other. Turning either on turns the other off, in the menu and in `applyStereo()`.
  - `src/stereo.c` gained a mid/side output shape alongside the existing one-sided Haas one. The dry signal goes into *both* channels and a short ensemble of four decorrelated taps (1.5-7.5 ms, mixed-sign gains) supplies the side signal. Because both channels carry the onset undelayed, the precedence effect that makes Stereo lean left cannot occur, and the two channels sum back to the original signal.
  - Measured: the channels reconstruct the mono mix to within 1 LSB (`Stereo`/Haas is off by up to 21924 LSB from comb filtering), the inter-channel delay is 0 frames (`Stereo`/Haas at Wide is 264 frames), inter-channel correlation is 0.64, and per-channel level is within 0.62 dB of mono.
  - The cost is that each channel gets a mild comb from the tap ensemble, roughly 3 dB of ripple at the tap spacing. Unlike the Haas comb this is heard in stereo too. `SURROUND_GAIN` and the tap gains in `src/stereo.c` are the tuning constants.
  - `varz.c`/`varz.h` gained `surround_enabled`; `config.c` persists `[audio] surround`.
  - The Sound sub-menu now uses all 8 slots of its `items[8]` array.
- Added an optional stereo widening effect, toggleable at Setup - Sound - Stereo (ON/OFF), off by default and separate from Reverb.
  - The SDL audio device is now opened with 2 channels instead of 1. The channel count was never negotiable, so this is required to have left and right channels at all; the effect being off writes identical values to both, so the audio is unchanged until it is switched on.
  - `src/loudness.c` now mixes into a mono scratch buffer, because the OPL emulator, the SFX mixer and the reverb are all mono, and spreads it across the output channels at the very end. The existing mix, volume and reverb code is otherwise untouched.
  - Added `src/stereo.c`/`src/stereo.h`: a Haas-style widener that delays the upper spectrum in the right channel. Everything upstream is mono, so there is no side signal to amplify and the channels have to be decorrelated instead. The extreme bass is held back with a single one-pole lowpass so it stays common to both channels (measured side/dry 0.217 at 80 Hz versus 0.479 at 6 kHz). One section is deliberate: the widened signal is the complement of that lowpass, so stacking sections would raise the widened signal and defeat the purpose.
  - The delay line runs continuously with a ~30 ms crossfade on the right channel, so toggling cannot click, and at zero width the dry sample is copied directly so the off state is bit-identical to plain duplication.
  - Note that any mono-to-stereo widener comb-filters when downmixed to mono, so this is less clean on mono speakers. It is off by default for that reason.
  - Added `Setup - Sound - Stereo Width` (Narrow/Normal/Wide). The inter-channel delay is a straight tradeoff: a longer offset decorrelates tonal audio more and so sounds wider, but the ear also localises a sound towards whichever channel arrives first, so a wider setting leans the image further left. Measured inter-channel delay is 1.5, 3.0 and 6.0 ms for the three presets, and Normal is the default.
  - Changing the width mid-song cannot click: the crossfade is collapsed to zero first and the delay is swapped while both channels are bit-identical, so the swap is inaudible.
  - `varz.c`/`varz.h` gained `stereo_enabled`, `stereo_width` plus `applyStereo()`; `config.c` persists `[audio] stereo` and `[audio] stereo_width`.
  - The Sound sub-menu now uses all 7 slots of its `items[7]` array; any further Sound option needs that array widened.
  - `visualc/opentyrian.vcxproj` now lists `reverb.c`/`reverb.h` and `stereo.c`/`stereo.h`, and also the previously missing `drawlist.c`, `drawlist.h`, `interp.c`, and `interp.h` entries, so the MSVC project builds every source file.

## Build/Performance
- Replaced direct frame pacing with an interpolation-based 60 Hz presentation layer. The original logic tick rate is preserved; gameplay logic continues at the original cadence while the presented frame is interpolated/presented at the display refresh rate.
  - Added `src/drawlist.c`/`src/drawlist.h` as a per-tick recording layer for sprites, background rows, rectangles, fills, darken effects, filters, starfield, and superpixel passes into a tagged emitter, so replay/interpolation can be reconstructed.
  - Added `src/interp.c`/`src/interp.h` for decoupled presentation. presentation uses vsync pacing with a soft display-refresh fallback.
  - Wired recording contexts (`DL_OBJ_*`) through `tyrian2.c`, `mainint.c`, `shots.c`, `sprite.c`, `vga256d.c`, `backgrnd.c`, `varz.c`, `video.c`, and `drawlist.c`.
  - `nortsong.c/nortsong.h` gained frame deadline/period getters (`getFrameDeadline`, `getFramePeriod`).

## Controls/Movement
- Removed player ship inertia: ship acceleration towards target was removed in `src/mainint.c` (`accelXC += this_player->x - *mouseX_;` and `accelYC += ...` commented out), eliminating drift and ghosting ship motion.
- Keyboard/manual movement:
  - `CURRENT_KEY_SPEED` set to `5` in `src/varz.h`.
  - Added diagonal-aware handling in `src/mainint.c` and reduced diagonal speed via `CURRENT_KEY_SPEED_DIAGONAL` set to `4` in `src/varz.h`.

## Rendering/Interpolation Timing
- PIT/original delay logic restored to original cadence after an earlier 60 Hz presampler experiment was reverted; `nortsong` retains only deadline/period getters used by the interpolation layer.
- `Setup > Graphics > Smooth Motion` toggle added for the 60 Hz presentation, and persisted as `[video] smooth_motion` in `opentyrian.cfg`. It defaults to on, matching the previous hardcoded `interp_smooth_motion = true`. Turning it off restores the original single-frame path (`wait_delay()` + one `JE_showVGA()` per tick) with no draw-list recording at all, which makes the interpolated presentation directly comparable against it. `interp_active()` re-reads the flag every tick and `drawlist_set_smooth_enabled()` resets the recorded history on the transition, so no apply step is needed.
  - The flag is inert on Detail Level 5 (Nonstandard VGA), which still forces `smoothScroll = false` and therefore fails `interp_active()`'s gate.
- **Detail Level 3 (High Detail) now blends clouds and keeps the 60 Hz presentation.** It previously set `smoothScroll = false` and left `wild = false`, which had two independent effects that both read as "this level looks broken":
  - `wild == false` sends all three cloud draw sites (`tyrian2.c`'s `background2over == 0/1/2`) to the opaque `draw_background_2()` instead of `draw_background_2_blend()`. With `background2over == 1` the cloud is drawn *after* `JE_drawEnemy(50)/(100)`, so enemies under it were fully hidden. High Detail now takes the 50/50 low-nibble blend like Pentium, and they show through again. `wild` is read nowhere else in the tree apart from those three call sites, so this cannot affect anything else; `superWild` and `filtrationAvail` are still off at this level.
  - `smoothScroll == false` made `interp_active()` return false, so the whole 60 Hz presentation layer was dormant on this level and nothing was even recorded. It also meant `interp_present_gameplay()`'s classic path skipped `wait_delay()`/`setDelay()` entirely, leaving the tick unpaced. High Detail now keeps `smoothScroll = true`.
  - This matches how Detail Level 2 (the 486 default) is configured; only High Detail and Nonstandard VGA were held back.

## UI
- Setup menu hint text no longer runs off the right edge of the screen. The description was drawn left-aligned at `xMenuItemName` (45) with no width limit, so anything wider than the 275 pixels left to the screen edge was clipped. Three of the sixteen were: Smooth Motion measured 390 px (114 px off-screen), Stereo Width 328 px (57 px) and Surround 300 px (25 px). Widths are measured against the tiny font loaded from bank 2 of `tyrian.shp`, where glyphs are 4 px wide plus a 1 px advance and a space is a hardcoded 6 px in `fonthand.c`.
  - Note the cause is horizontal overflow, not a collision with the value column. The value display sits at `xMenuItemValue` (180) but spans `y = 37..163`, while the hint is drawn at `y = 190`, so the two never shared a row to begin with.
- The hint is now centred on `xCenter` rather than left-aligned at the item names, which moves all sixteen of them — "Change the graphics settings." goes from x=45..181 to x=92..228. Centring is what makes the overflow visible to fix, since the previous left-aligned layout hid most of it past the item-name column.
- Rewrote the two descriptions that were simply too long to sit comfortably on one line, which is the actual fix rather than reflowing them. Smooth Motion goes from "Interpolate between logic ticks so the game presents at the display refresh rate." (390 px, 81 chars) to "Interpolate logic ticks for a smooth display." (208 px), and Stereo Width from "How far apart the Stereo channels sit. Wider is wider but leans left." (328 px, 69 chars) to "Stereo separation. Wider is wider but leans left." (227 px). Both keep the part that carries meaning — that wider leans the image left is still stated, since it is a real audible tradeoff.
- The wrap threshold is a dedicated `wHint` (300 px), not `wMenuItem` (230 px). `wMenuItem` is 230 only because the name column is 135 and the value column 95; the hint is a full-width line beneath the menu and shares no row with either, so its natural bound is the 320 px screen less a 10 px margin at each side. Measured against the real font, the widest hint is now Surround at 300 px, spanning x=10..310 centred, so all sixteen render on one line and none reach the threshold. The wrapping code itself is kept as a safety net: a description over 300 px splits at the word boundary nearest the midpoint, onto y=178 and y=190, rather than running off-screen. Splitting at the midpoint rather than filling greedily matters — a greedy fill pushes 203 px onto the first line of "Widen the sound across the left and right channels." and leaves " channels." on the second, against 130 px / 114 px balanced.
- Worth recording because it cost most of the time spent here: wrapping was tried first, at a 230 px threshold, and it was the wrong fix. Wrapping only helps descriptions that are *slightly* too long. At 81 and 69 characters, Smooth Motion and Stereo Width split into two lines that were both still heavy (190/193 px and 152/174 px), and the split was ugly as well as ineffective — short enough that it did not fix the complaint, ragged enough to look worse than one line. The threshold was also wrong in a way that was not obvious: an intermediate build wrapped at `wMenuItem` and Stereo (246 px), Small Hitbox (255 px) and Surround (300 px) were measured as over it, but in the running game all three rendered on a single line. Those three are now comfortably under `wHint`, so which measurement was right no longer matters, but the discrepancy was never explained. Both changes were needed: the copy was the actual problem, and the threshold was simply not the constraint it appeared to be.
- Known limit, recorded so a future description is checked against it: the picker box is clamped by `MIN(yPicker, 200 - 10 - (hPicker + 5 + 2))`, which lets its bottom edge reach y=187 and would swallow a wrapped first line at y=178..184. Nothing wraps today, but if a description is ever raised past 300 px, check which item it sits on: the Scaler picker is the one that reaches 187 (nine items). The last item row is not a constraint, since the deepest is Sound - Done at y=163, which bottoms out at 174.

## Fixes
- Fixed the draw list interpolating a new level's first frame against the *previous* level's command list. `drawlist_level_reset()` cleared `dl_last`, `dl_have_prev` and `dl_ref_valid` but not `dl_sets[i].count`, and `drawlist_frame_end()` derives `dl_have_prev` from the other set's count — so that count stayed non-zero across a level change and the first tick of every level paired against stale positions, stale background `map` pointers and stale sprite sheets.
- The byte-exact replay/interpolation checks in `drawlist.c` had no callers and no command-line flag, so they never ran even though the frame the 60 Hz presentation actually shows is the *replay* (`interp_present_gameplay()` copies from `drawlist_interpolated_game()`, not from `game_screen`) and any replay infidelity is therefore unconditionally visible. They are now reachable:
  - `--regress-replay-check` arms `drawlist_set_check()`, which replays each recorded tick and compares it byte for byte with the live frame.
  - `--regress-interp-check` arms `drawlist_set_interp_check()`, which renders through the interpolated renderer at alpha = 1 — the exact frame presented at the end of every tick — and compares that. This is the one that matters for the 60 Hz path.
  - Both register `atexit(drawlist_print_check_summary())`, which reports frames checked, frames differing and the first differing pixel. If the two flags are given together the first one wins, since `drawlist_frame_end()` treats them as mutually exclusive arms.
  - **They write `drawlist-regress.log` next to `opentyrian.cfg`**, truncating it per run, and report into it *as frames are checked* rather than only on exit. This is not a nicety: the game links as a GUI-subsystem PE, so `stderr` is discarded unless the parent explicitly redirects it, and a run launched by double-clicking the `.exe` produced no evidence at all. Each write is flushed, so even a hard kill leaves the log usable. stderr still receives everything, for the case where it is redirected.
  - A run that arms a check but never reaches a level now says so explicitly ("no frames were checked"). Previously "armed but never ran" and "never armed" were both entirely silent and therefore indistinguishable — a mistyped invocation looked exactly like a clean pass.
  - A systematically wrong level previously printed one stderr line per mismatching tick; the report is now emitted for the first mismatch and then only every 300th, on the same cadence as the progress lines.
